# jit Build Roadmap

A persisted record of the build plan and its status — this mirrors an in-session task tracker used while building jit, written down here so it survives across sessions and is visible to anyone reading this repo cold, not just kept in a tool that would otherwise lose it. Update this file as tasks complete or new ones get added; treat it as the source of truth for "what's done and what's next."

Related docs: [`RFC.md`](./RFC.md) (architecture/threat model), [`TECH_STACK.md`](./TECH_STACK.md) (implementation choices).

---

## Pre-Launch Decisions

- [x] **Decide OSS license and open-core boundary.** Apache License 2.0 adopted (see [`LICENSE`](./LICENSE)). Chosen over a source-available license like BSL because BSL's core protection — blocking someone from re-hosting the code as a competing service — doesn't apply to jit's shape: Phase 1/2 has no server component at all, so there's nothing to re-host. The realistic competitive risk (incumbents building similar features) is a product race, not a code-forking race, and a license doesn't defend against that either way. Open-core boundary unchanged: the Future Enterprise Tier stays a separate product/codebase, not a license-gated feature in this repo.
- [x] **Publish `SECURITY.md` and vulnerability disclosure process.** Routes to GitHub's private vulnerability reporting rather than a personal email (a personal inbox is a solo-maintainer single point of failure). **Manual step still open, blocked on going public:** enable "Private vulnerability reporting" in this repo's Settings → Security → Code security. The API 404s (and the UI toggle doesn't exist) because GitHub only offers this feature on PUBLIC repositories — the repo is currently private, so this literally cannot be enabled yet. Do it as part of the public-release flip, not before.

## Phase 1 Build

Build order matters here: audit first (zero risk, delivers the primary goal standalone), then the fix path, then the mechanisms that make the fix hold up under real use.

- [x] **Build `jit audit`** (read-only risk scanner). All 7 RFC §4 categories (shell configs, `.env` files, credential files — AWS/kubeconfig/npmrc/Terraform Cloud/GCP — MCP configs, private keys, IaC files, suspicious filenames), the shared signal/redaction infra, scan orchestrator + risk-level aggregation, human-readable + NDJSON output, and CLI wiring (`jit audit`, `--format`). Fully tested (including real generated key material for the private-key scanner and a real built-binary end-to-end run against a fixture `$HOME`). Several real bugs and real-world-data lessons caught along the way — see commit history from 2026-07-06 for details (the `PROD_DB_URL` keyword gap, the CA-bundle-vs-key content-sniffing distinction, the suspicious-filename false-positive lesson, a Cobra `Execute()` gotcha). No vault/crypto dependency yet — that's next.
- [x] **Build local encrypted vault + `jit vault set`/`get`/`list`/`rm`/`init`** (Pillars I & II). Atomic file-per-secret storage (`internal/vault`, JSON envelope matching RFC.md's schema exactly) with per-secret AES-256-GCM DEKs, wrapped by a `KeyWrapper` interface rather than a hardcoded mechanism. Real spike work found the planned Secure-Enclave-backed MEK persistence is blocked on the same unresolved Developer ID signing issue as before — and, more precisely, that *any* `SecAccessControl`-gated keychain item hits `-34018` under ad-hoc signing, not just Secure-Enclave-token keys (`spike/keychain-interim-key/FINDINGS.md`). Shipped `internal/keychainwrap` as the interim `KeyWrapper`: a plain keychain-stored MEK gated by an application-level `LAContext` Touch ID/passcode challenge on every use — a real prompt, honestly documented (RFC.md B9) as weaker than OS-enforced ACL/Secure Enclave binding. Verified end-to-end on real hardware (real Touch ID prompts, correct decrypt round-trip) since interactive biometric approval can't be scripted. `internal/secureenclave` is where the target implementation swaps in later behind the same interface. Vault commands live under `jit vault` (not flat `jit set`/`get`) to group all vault CRUD under one namespace, matching `jit audit` staying un-namespaced as a workflow command rather than vault CRUD.
- [x] **Build `jit migrate --dry-run`** (`internal/migrate`) — a separate command from `jit audit`, not a flag on it, so the read-only audit tool can never be turned into a mutating one by a mistyped flag. Re-runs the same scan and categorizes every finding into three buckets: **ready** once `jit run`/`jit export` ship (shell-config secrets, MCP-embedded secrets — anything a plain env-var injection can restore), **blocked** on infrastructure that doesn't exist yet (`.env` files needing the live-mounted pipe, task #10; structured credential files needing a native credential helper or mount), and **manual** (private keys, IaC variable files, suspicious filenames — RFC.md scopes these detection-only). Only `--dry-run` is implemented: real mutation would strip a secret from wherever some tool currently reads it with nothing yet in place to restore it, a regression rather than a fix, so `jit migrate` without the flag fails loudly instead of pretending to do something. Verified end-to-end against a real fixture `$HOME`.
- [x] **Build named profiles + `jit doctor` preflight.** `internal/profile` implements the Pillar IV manifest format (`.jit/profiles/*.yaml`, project-scoped and git-safe — a named view over the vault tree, never ciphertext or values). `jit doctor` (`--profile <name>`, or every profile under `.jit/profiles/` by default) checks each referenced secret path actually exists in the vault, failing loud with the named missing variable/path instead of letting an app crash later on an empty env var. Existence-only, never decrypts — never needs local auth, safe to run as often as `jit audit`. Extracted `vaultRootDir`/`openVaultReadOnly` into a shared, portable (non-darwin-gated) `internal/cli/paths.go` so doctor doesn't pick up an unnecessary CGo/keychain dependency it doesn't need. Verified end-to-end against a real fixture project + vault.
- [x] **Build `jit run` (process injection) + `jit export`.** Tier 1 process-overwrite injection (`syscall.Exec`/execve) and materializing a profile into the current shell session. `internal/inject` resolves a profile's secrets against the vault (`MergeEnv` de-duplicates any key a profile overrides rather than relying on undefined duplicate-`environ` behavior across libcs) — fully unit-tested with a fake `KeyWrapper`, plus `jit run`'s `resolveRunPlan` (everything up to the actual `syscall.Exec` call, split out specifically so it's testable without exec'ing the test binary itself). Verified end-to-end on real hardware: `jit run --profile demo -- printenv DEMO_GREETING` correctly printed the real vault-decrypted value, confirming the Touch ID-gated `openVault()` path and `syscall.Exec` process replacement both work correctly together. First verification attempt used a fixture `$HOME`, which broke — macOS's own Keychain Services resolves the login keychain relative to `$HOME` too, so faking it broke Touch ID entirely (a test-setup mistake, not a product bug; corrected by using the real `$HOME` with only the profile/project directory faked, same as task #6). Also surfaced and resolved along the way: a *second*, separate macOS keychain-access-control prompt (distinct from jit's own Touch ID challenge) asks whether a given code signature may read an existing keychain item at all — expected to reappear on every dev rebuild (ad-hoc signing changes the signature each time) but a one-time approval for a real, stably-signed release build. Also fixed: `internal/keychainwrap`'s test suite was sharing the real production keychain service identifier (`com.jitpass.vault.mek`) with its own cleanup step — on a machine with a real vault already set up (this one), that's one click away from a test deleting the real MEK and permanently orphaning every stored secret. Tests now use a dedicated `com.jitpass.vault.mek.TEST-ONLY` identifier, verified never to touch the real item. Also added: MEK caching within a single `Wrapper` instance's lifetime, so a multi-secret profile only prompts Touch ID once per `jit run`/`jit export` invocation, not once per secret.
- [x] **Build live `.env` mounting** (Tier 3). `internal/mount` promotes the re-opened named-pipe mechanism validated in `spike/named-pipe/` into real code (`Serve`, `CreateFIFO`, dotenv-format content rendering) plus a small registry (`mounts.yaml`, alongside the vault) recording which profile serves which mount. `jit migrate` (real, non-`--dry-run` mode) converts real `.env` files found under the *current directory tree* — deliberately narrower than `--dry-run`'s whole-machine preview, since rewriting files across every unrelated project under `$HOME` in one command would be a much bigger blast radius than fixing the project you're standing in — into a profile + vault secrets + FIFO mount, in that order (never destroying the original file until everything else has succeeded). `jit agent` (new command) reads the registry and serves every mount until Ctrl-C or `--ttl` elapses (default 15m) — a real, explicitly-run process, not an auto-spawned background daemon.
  **Deliberate, documented gap:** RFC.md B10 requires gating the mount per-reader by process lineage before it's a strict upgrade over the pointer-rewrite baseline it replaces ("shipping the mount without read-time gating is a regression... not an upgrade"). That gating is explicitly Phase 2 scope (RFC.md §5.1) and needs an unvalidated mechanism for identifying a FIFO reader's process — the peer-credential approach already spiked (`spike/unix-socket-peercred/`) only covers Unix sockets, not named pipes. Shipped ungated for now, any process that opens the path gets the real content (no different from reading a plaintext file today) — decided explicitly rather than silently shipped as if it met B10's bar.
  **Real bug found and fixed during manual verification:** the first version of `Serve` treated a write/close error as fatal and returned, silently killing the whole mount after serving exactly one reader — reproduced live when a second `cat .env` got nothing right after a first one succeeded. Root cause: a reader that opens and closes without draining the pipe (a normal, common pattern) can race the write and produce a transient "broken pipe," which the reference `spike/named-pipe/` loop only logs and continues past, not something to abort on. Fixed by adding an `onError` callback that reports but never stops the loop; locked in with `TestServeContinuesAfterReaderClosesEarly`, which deterministically reproduces the race with an oversized payload. Re-verified end-to-end afterward: three sequential `cat .env` reads against one `jit agent` process all returned the correct decrypted content.
  **Superseded by the persistence fix below:** `jit agent` described here (a one-shot process serving mounts until `--ttl` then exiting) was replaced by a real, launchd-managed persistent process — see "Post-Phase-1 Fixes."

## Post-Phase-1 Fixes

Real gaps found via `GAPS.md` after Phase 1's core build, fixed one at a time.

- [x] **`jit agent` persistence + shared session broker** (closes `GAPS.md` #10 and #11). `internal/agent` now implements RFC.md Pillar II's session broker for real: a Unix-socket `Server` (peer-verified same-user, `spike/unix-socket-peercred/`'s mechanism) holds the decrypted MEK in memory for up to `--ttl` (default 15m) after the most recent unlock, answering `wrap`/`unwrap`/`unlock`/`lock`/`status`/`refresh` RPCs from other jit processes via `Client`. `jit agent install` registers it as a real launchd LaunchAgent (`RunAtLoad`, `KeepAlive`) — validated first via a throwaway spike (`spike/launchagent-touchid/FINDINGS.md`) that a LaunchAgent-launched process can actually show a Touch ID dialog, unlike a headless/automated one. The process itself now runs indefinitely without needing Touch ID; only the cached MEK inside it locks after the TTL (a `time.AfterFunc` timer, not just lazily detected on next use) and re-challenges on next request — mount-serving is tied to these same unlock/lock transitions via `OnUnlock`/`OnLock`/`OnRefresh` hooks, not resolved eagerly at process startup (a `RunAtLoad` agent starting before anyone's at their desk must never trigger a surprise prompt). `jit vault get/set`, `jit run`, and `jit export` (`openVault()`) all transparently prefer a reachable agent's shared session over their own independent unlock. Verified end-to-end on real hardware: a full `install` → `migrate` → `lock` → `uninstall` sequence needed exactly one Touch ID approval.
  **Two real bugs found and fixed during that verification:**
  1. The client's response timeout (5s) was far shorter than the underlying challenge's own ceiling (120s in `kw_challenge`) — a slow-to-approve prompt produced a spurious client-side "i/o timeout" error even though the unlock succeeded moments later (confirmed: the next `agent status` showed correctly unlocked). Fixed by splitting a short dial timeout (5s, "is anything listening") from a 130s response timeout ("wait for a reply, which might be behind an interactive approval"). Locked in with `TestClientToleratesSlowChallenge`.
  2. `jit migrate`'s own first vault write triggers the very unlock that fires `OnUnlock` and starts mount-serving — but that happens *before* the new mount is registered, so that scan finds nothing yet, and the mount silently never gets served (any read against it just hangs, reproduced live: `cat .env` hung with no output). Fixed by adding an explicit `OpRefresh` RPC `jit migrate` sends the running agent right after registering a mount, and by making mount-serving *incremental* (`mountManager.start` is idempotent and only starts genuinely new entries, callable repeatedly) rather than an all-or-nothing "already running, skip" guard that would have missed the second bug's fix too. Locked in with `TestServerRefreshCallsOnRefreshAndEnsuresUnlocked`.
  **Still true and unchanged by this fix:** `GAPS.md` #1 — Touch ID is application-enforced (`LAContext`), not OS-enforced; sharing one unlocked session across commands changes how *often* you're asked, not *who* could reach it with existing code execution as the same user.
- [x] **`jit migrate` warns about git history** (closes `GAPS.md` #3). `internal/migrate.HasGitHistory` checks `git log --oneline -- <file>` for any commit that ever touched the file, not just current tracked status — a file someone already tried to "fix" by deleting it and adding it to `.gitignore` is still correctly flagged, since the old plaintext value is still recoverable from history regardless. `jit migrate` prints an explicit warning (with a pointer to `git-filter-repo`/BFG Repo-Cleaner, matching RFC.md B7's own suggested fix) before migrating any file with history — a warning, not a block, since moving the value into the vault is still the right next step even for an already-committed file. A missing/broken git installation or a non-git directory is treated as "nothing to warn about," not an error. Verified end-to-end on real hardware against a real git repo with a committed `.env`.
- [x] **`jit unmount`** (closes `GAPS.md` #12). `jit unmount <path>` decrypts a mount's secrets from the vault and writes them back out as a plain dotenv file, replacing the FIFO — `internal/migrate.UnmountEnvFile` mirrors `ApplyEnvFile`'s reverse direction, adding `mount.FindMount`/`RemoveMount` as the registry-side counterparts to `AddMount`. Deliberately leaves the vault secrets and profile manifest in place — this reverses the *file*, not the whole migration. If `jit agent` is running, `unmount` calls the already-built `Client.Lock()` first, guaranteeing nothing is mid-`Serve()` on the FIFO before it gets replaced with a regular file — skipping this would risk a real race (the agent's next write landing on the caller's fresh plaintext, since opening a regular file for write never blocks the way a FIFO does). Locks the whole agent, not just this one mount (no per-mount stop exists yet) — `jit agent unlock` resumes any other mounts afterward. Verified end-to-end on real hardware: `migrate` → `unmount` round-tripped both variables back to their exact original plaintext values.
- [x] **`jit migrate` extended to shell-config and MCP secrets** (closes `GAPS.md` #7). `internal/migrate/shellconfig.go`'s `ApplyShellConfig` moves secret-shaped `export KEY=value` lines out of `.zshrc`/`.bashrc`/etc. (checked regardless of the current directory — these live at a fixed home path either way) and replaces them with one `eval "$(jit export --profile ...)"` call. `internal/migrate/mcpconfig.go`'s `ApplyMCPConfig` moves an MCP server's env-block secrets into the vault and rewrites its `command`/`args` to launch via `jit run`, using jit's own resolved executable path (not a bare "jit" — a GUI-launched host's `PATH` often doesn't match a shell's). Both back up the original file first (`<file>.jit-bak-<ts>`), a bigger safety margin than `.env` migration needed, since a mistake here breaks every future shell session or MCP server launch rather than one file. Neither secret is project-scoped, so both use a new home-rooted global profile store (`profile.GlobalRoot`, resolved via a design discussion with the user up front) that `profile.Load` falls back to when a project-relative lookup misses — the alternative of scoping the whole feature down to shell-config-only was explicitly declined in favor of solving profile resolution once, for both.
  **Real incident found during verification:** a pre-existing test (`TestMigrateWithoutDryRunNoEnvFiles`) isolated only the working directory, not `$HOME` — safe before this change, unsafe once real mode gained home-scoped discovery on the same code path. Running the test suite actually executed real migration against the real machine, moving three real secrets from a real Claude Desktop MCP config into the real production vault and breaking that server's launch command (rewritten to the ephemeral `go test` binary's path). `ApplyMCPConfig`'s own backup-before-rewrite is what made this recoverable — the original file was restored from its auto-created backup and verified byte-identical, and the incidental vault/profile residue was removed with the user's explicit confirmation. Fixed by isolating `$HOME` in that test too. See `GAPS.md`'s Resolved entry for #7 for the full account.
- [x] **`jit migrate` extended to AWS/kubeconfig/npmrc credentials** (closes `GAPS.md` #8; Terraform Cloud/GCP application-default-credentials deferred as new `GAPS.md` #16). `internal/migrate/awscreds.go` (Tier 2): moves an AWS profile's static keys into the vault, adds `credential_process` to `~/.aws/config` under the right section name (AWS's own bare `[default]` vs `[profile <name>]` irregularity), and the new `jit aws-credential-process` subcommand prints the exact JSON the protocol requires. `internal/migrate/kubeconfig.go` (Tier 2): moves a bearer token or client-cert/key pair into the vault, replaces it with an `exec` block, and the new `jit k8s-exec-credential` subcommand prints the matching ExecCredential JSON. `internal/migrate/npmrc.go` (Tier 4): unlike the other two, npm has no native credential hook and npmrc mixes secrets with ordinary settings that must survive untouched, so this needed genuinely new mount infrastructure — `internal/mount.FormatTemplate` substitutes `${VAR_NAME}` placeholders into an otherwise-verbatim template, and `mount.Entry` gained an optional `TemplatePath` the agent's `mountManager` and `jit unmount` (`UnmountEnvFile` renamed `UnmountFile`, now template-aware) both branch on. All three back up the original file(s) first, and — since none of these secrets are tied to a project directory the caller invokes from (AWS CLI/kubectl/npm all resolve from an unpredictable cwd) — all three use the home-rooted global profile store `profile.GlobalRoot` built for gap #7.
  **Two real bugs found and fixed, both caught by directly running the new tests:** (1) `npmrcVarName`'s sanitizer left a double underscore when a replacement character sat next to an original literal underscore (e.g. `/:` before `_authToken`) — fixed with a collapse-repeated-underscores pass, caught by `TestNpmrcVarNameSanitization`'s exact-match assertion. (2) `DiscoverNpmrcFiles` never guarded the fixed global `~/.npmrc` path against already being a FIFO before reading it — opening a FIFO for read blocks forever until a writer connects, hanging a second migration attempt with no agent running; fixed with the same `os.Lstat`+`ModeNamedPipe` guard `DiscoverEnvFiles` already uses for its own walk, caught by a test timing out with the hang's exact stack trace rather than passing silently. Verified via the full automated suite with `$HOME`/cwd isolated in every new test, directly applying the gap #7 incident's lesson — not yet verified end-to-end against a real AWS/kubectl/npm invocation on real hardware.
- [x] **Live `.env`/npmrc mount gated decoy-by-default** (closes `GAPS.md` #2, resolves RFC.md B10 — not via the per-reader-identity mechanism originally planned). `spike/fifo-reader-identify/FINDINGS.md` first tested both identity-based candidates for real: Apple's Endpoint Security framework turned out impractical for jit's bare-binary/Homebrew distribution shape (a discretionary, often multi-month-or-longer entitlement that would also force an app-bundle/System-Extension repackage) and was evaluated-and-parked rather than queued; the cheaper unprivileged `libproc` scan works (same-UID-only, sub-millisecond) but has a real, reproduced race — a reader that closes fast enough evades identification — making it unsafe as a hard gate. The fix inverts the approach instead of chasing a better identification mechanism: `internal/mount.RevealState`/`DecoyValues` make a mount serve fake-looking values by default and real values only during a short, explicitly-revealed window, so exposure is bounded by *when* rather than *who*. `mount.Serve`'s signature changed to a `provideContent func() []byte` called fresh every re-open cycle, strictly after a reader connects but before anything is written — the ordering that makes the gate race-proof against exactly the timing attack that defeated identity-based gating.
  Revealing has three layers, each funneling through the same Touch-ID-or-cached-session `ensureUnlocked` gate `jit vault`/`jit run` already share: automatic (every agent unlock/`jit migrate` refresh reveals all known mounts for 60s), explicit (`jit agent reveal <path> [--for D]`, a new `OpReveal` RPC mirroring `OpRefresh`'s existing pattern, clamped server-side to a 10-minute ceiling), and automated (`jit migrate`'s new `internal/migrate.InstallRevealHook` best-effort wires the explicit reveal command into an existing `.envrc` or `package.json`'s `dev`/`start` scripts — installs at most one hook, never creates a `.envrc` a project didn't already have, and does nothing rather than guess for docker-compose/Makefiles/IDE run configs). `internal/lineage` (the third CGo/darwin-only package, alongside `internal/keychainwrap`/`internal/secureenclave`) promotes the spike's scan into real code as a best-effort audit log wired into `Serve`'s new `onReaderConnected` hook — deliberately kept separate from the content-selection hook so reader identity can never influence what gets served, only what gets logged.
  **A real, pre-existing bug found (not introduced) while testing this under `-race`:** `Serve`'s re-open loop can occasionally let one reader receive two cycles' content concatenated, if the previous reader hasn't fully disconnected by the time the loop re-opens for the next cycle — confirmed via `git stash` to reproduce on unmodified `main` too, invisible under a plain `go test` run (this project's CI doesn't use `-race`), so it was never caught before. Documented as new `GAPS.md` #24 rather than fixed here — needs its own design pass, and has only a narrow, unconfirmed bearing on this gate (a race landing exactly at a reveal/hide boundary).
  Verified via the full automated test suite (`RevealState`, `DecoyValues`, `Serve`'s before-write ordering guarantee, `OpReveal`, `InstallRevealHook`'s direnv/npm paths, `internal/lineage`'s libproc scan) — not yet verified end-to-end against a real dev workflow on real hardware.

- [x] **Reveal-mechanism investigation fixes** (closes `GAPS.md` #46-#49, found by investigating a real "jit agent reveal isn't working" report — the reveal gate itself was verified correct; four defects around it made it look broken). #46: `jit agent reveal` reported success and status showed a live countdown on a mount whose secret resolution had failed — every read served decoys with the error visible only in the agent's log; reveal now refuses with the recorded resolve error, and the post-unlock auto-reveal window is granted only to mounts that actually resolved. #47: the per-cycle `recreateFIFO` rename is a filesystem event, and a file watcher that re-reads on change (VS Code with the project open) turned it into a self-sustaining loop — ~30 reads/sec for hours, 635k log lines, 63 CPU-minutes in one afternoon; fixed in two layers (EPIPE-proven reuse, then a `lineage.PathHeldOpen`-gated skip of the rename when no reader lingers — the one argued exception to "lineage never gates," content-free by construction), verified live: 0 reads/min with the same VS Code tab open. #48: a reveal window's end was invisible (the status line silently vanished; the agent log had no timestamps) — status now reports "last reveal window ended Xm ago" and `jit agent run` timestamps every log line. #49: launchd's `KeepAlive` keeps a stale agent process alive across rebuilds with no way to notice; every status RPC now carries the agent's build ID and `jit status`/`jit agent status` warn on mismatch with the CLI's own. Verified end-to-end on real hardware, including the live watcher-loop measurement and a real stale-agent mismatch warning.
