# Known Gaps

A single, honest list of everywhere jit's current behavior falls short of its own target design — consolidated from RFC.md's blast-radius table (`B1`–`B10`), ROADMAP.md's task notes, and the project's working conventions, so there's one place to see the whole picture instead of three. The project's "fail safe and loud" principle applies to documentation too: a gap that's written down and understood is very different from one that's silently discovered later.

Each entry links to where it's discussed in more depth. Status changes as gaps get closed — update this file (and the source doc it points to) together, don't let them drift apart.

---

## Security-model gaps (accepted tradeoffs already shipped)

| # | Gap | Detail |
|---|---|---|
| 1 | **Vault Touch ID isn't OS-enforced.** | `internal/keychainwrap`'s challenge is application code (`LAContext.evaluatePolicy`), not a real Keychain ACL/Secure Enclave binding. A determined attacker with existing code execution as you could bypass the app-level check and read the keychain item directly. **Not merely blocked on a signing identity** (a common misconception, now corrected): a real Apple Development identity was obtained and tested 2026-07-11, and the Secure-Enclave persistent-key path *still* fails `-34018` — it needs a provisioning-profile-authorized entitlement that can only be embedded in an `.app` bundle, so it can't work in jit's bare-CLI `go install`/Homebrew-formula shape at all. Deferred (adoption-gated) to a notarized `.app`-wrapped jit-agent — see `spike/secure-enclave/FINDINGS.md`'s 2026-07-11 update, `spike/keychain-interim-key/FINDINGS.md`, and RFC.md B9. |
| 4 | **The secret is plaintext inside whatever process it's injected into.** | `jit run`/the live mount only narrow the exposure window (no idle file on disk, TTL-bound) — they don't and can't sandbox a compromised dependency running inside the target process. RFC.md B1. |
| 5 | **"Biometric-bound" is really "OS-local-auth-bound."** | Touch ID falls back to the device passcode/password per macOS defaults; that's the actual guarantee, not strictly biometric. RFC.md B9. |
| 6 | **Named pipes can't serve true random access.** | `stat` for real size, `lseek`, `mmap` don't work against a FIFO on any POSIX system — fine for normal dotenv loaders, breaks anything that needs real file semantics. RFC.md B4. |

## Known bugs (found, not yet fixed)

| # | Gap | Detail |
|---|---|---|
| 64 | **Two or more processes reading the same live mount at the very same instant: only one gets the content, the rest get an empty read.** | Found in the 2026-07-12 clean-slate DX test by stress-reading a mount: 30/30 *sequential* `cat`s of `.env` returned full content, but 20 *concurrent* ones returned content to only ~4 — the other ~16 read empty (2 concurrent → 1 empty; 3 → 1 empty). Root cause is POSIX FIFO fan-out, not a jit bug per se: `mount.Serve`'s loop does one `open`-for-write → single `Write(provideContent())` → `close` per cycle, and a single write's bytes are consumed by exactly ONE reader — every other reader that attached to that same writer-open sees EOF (empty) the moment the writer closes. The loop then serves the next reader on its next cycle, which is why *serial* readers are 100% reliable. `isolateHeldPipe`'s own comment already concedes "a brand-new reader that raced into this narrow window gets an empty read it can retry (rare)" — the DX test showed it isn't rare under genuine concurrency. Practical exposure is bounded: the reveal-hook model means the app is normally the *sole* reader after `npm run dev`, so the everyday path is unaffected; the trigger is several distinct processes opening the file within the same few milliseconds (an app + a file-watcher like nodemon/webpack + an editor's dotenv extension all booting at once), where one or more may transiently read empty and would need to re-read. No secret exposure (a losing reader gets nothing, never a wrong value). A real fix means either per-reader write cycles (the kernel gives no reliable signal of how many readers attached to one writer-open) or a different transport than a bare FIFO — same design frontier as #6/#58; belongs in the Phase 2 mount-hardening pass, documented here so it's a known limitation rather than a silently-discovered one. |
| 58 | **Any change-watching reader turns a served mount into a self-sustaining read storm — no rename event needed — and a live mount can hang VS Code's entire quit.** | Found investigating #57's incident, then fully reproduced on demand (2026-07-12, scratch project + agent log): baseline 0 reads/60s with the mount served and nothing open; the moment a VS Code window opened the project with `.env` as a tab, ~206 reads/30s (~7/sec, lineage-identified as VS Code's main process, sustained indefinitely, decoys rendering fine in the tab); closing the tab but keeping the window TRIPLED it (~1300 reads/30s, readers now opening/closing too fast for lineage to identify, half the serve writes hitting broken-pipe); quitting VS Code stopped it dead — and the quit itself HUNG on the open mount (force-quit required; an editor shutdown path blocking on pipe semantics is #6's class, but "quitting your editor hangs" is a much worse experience than "stat is weird"). Crucially the pipe's inode was STABLE across every cycle: #47's isolation-rename skip is working exactly as designed and is NOT the vector — the feedback needs no filesystem rename at all. Working hypothesis: the serve write itself is the change event (a pipe write updates its vnode state/mtime), so any watcher that re-reads on change re-triggers the very write it's reacting to; jit cannot suppress that signal. Direction: serve-side storm damping (per-mount reconnect backoff once cycles/sec crosses a threshold — bounds CPU/log damage and slows the loop without breaking a legitimate reader, which just blocks in open() briefly), plus documenting "don't keep a mount open as an editor tab." Belongs in the Phase 2 hardening design pass; the raw damage today is CPU/log noise + the quit-hang, not secret exposure (the storm reads decoys unless revealed). |

## Resolved

- **#73 (`jit audit` reported jit's own live mounts as high-severity exposures — and could hang forever on them with no agent running).** Reported from real use (2026-07-13): after migrating five `.env` files, `jit audit` still flagged every one of them as `[high]` ("contains DESCOPE_MGMT_KEY, a variable name that looks like a real credential", etc.) — the scanner opened each mount's FIFO, read the DECOY content the agent serves to unrevealed readers, and reported jit's own protection as the exposure it exists to remove. Worse latent case: with no agent process writing, `os.Open` on a writerless pipe blocks forever, hanging the entire read-only scan. Fixed at the mode level, not the registry level: `walkHomeDir` now passes only regular files to scanners (a named pipe/socket/device has no at-rest content for an exposure scanner to judge, jit-made or not), and `scanNpmrc`'s fixed-path global `~/.npmrc` check — outside the walk — got the same `Lstat`+`IsRegular` guard, since `jit migrate home` can turn that file into a template mount too. The exclusion is visible, never silent: `Scan` counts registered mounts currently occupying their path as a pipe (`countProtectedMounts`, best-effort read of `mounts.yaml` via new `Config.MountRegistryPath`) into `scan_summary`'s new `jit_protected_count` (schema 0.2.0, additive), and both human and markdown reports print a green "Already protected by jit: N live mount(s)" line under the total — a registered path that's a regular file again is deliberately NOT counted and still scans as plaintext. `TestScanEnvFilesSkipsLiveMountFIFO` (which HANGS, not fails, on regression), `TestScanNpmrcSkipsGlobalLiveMountFIFO`, `TestScanCountsProtectedLiveMounts`, and `TestReportsShowProtectedCountOnlyWhenNonZero` lock it in; verified live on the machine that reported it — the five mounted files vanished from findings, the protected line shows 5, and the still-plaintext playground files still report.
- **#68 (`jit migrate undo` removed the reveal hooks but left `package.json` git-dirty — keys alphabetized, trailing newline dropped — after a "byte-for-byte" restore).** Found in the 2026-07-12 (round 3) full-CLI E2E test: a complete migrate→undo cycle ended with every secret file hash-identical to its pre-migration state, but `git status` still showed `M package.json` — #63's surgical hook removal worked, but it rides a JSON round-trip through Go maps (`map[string]json.RawMessage` in, `MarshalIndent` out) that reorders top-level keys alphabetically and drops the file's trailing newline. Fixed with `writeNpmHookFile` (`revealhook.go`): when the surgically-cleaned content is *semantically* identical to a `.jit-bak` sibling (the exact pre-install bytes `backupFile` kept), those original bytes are restored verbatim — a file the user edited since install never matches any backup and falls through to the surgical rewrite, which now at least preserves the original's trailing-newline convention. Wired into both `UninstallRevealHook` (undo's path) and `RemoveRevealHooks` (remove's path, which also gained the `.jit-bak` cleanup it was missing — leave-nothing-behind now includes the hook backups). `TestUninstallRevealHookNpmRestoresOriginalBytes`/`...UserEditFallsBackToSurgical`/`TestRemoveRevealHooksRestoresOriginalBytesAndCleansBackups` lock it in; verified on real hardware the same day (migrate→undo → `git status` shows nothing but `.jit/`).
- **#69 (`jit unmount` left the mount's `.pointers` companion — and its reveal hook — behind forever).** Found in the same E2E test: after `jit unmount services/api/.env`, the `.env.pointers` companion survived, and the later `jit migrate undo` didn't clean it either — undo's companion/hook cleanup was gated on the path still being a *registered* mount, which an already-unmounted file by definition isn't. Fixed on both sides: `jit unmount` now removes the `.pointers` companion and uninstalls the mount's own reveal hook right after deregistering (best-effort, warns but never fails the unmount that already succeeded), and undo's cleanup is unconditional — for a never-mounted record (a shell config, an `.mcp.json`) both cleanups are exact no-ops, and for a stale leftover from an older jit's unmount they now actually fire. Verified on real hardware: unmount → companion gone.
- **#70 (`jit vault import --stdin` driven by a script always failed "wrong passphrase" unless `--yes` was passed).** Found in the same E2E test: `printf 'y\n<passphrase>\n' | jit vault import --stdin <file>` — the documented confirm-then-passphrase order over one pipe — failed decryption every time. `confirmPrompt` wrapped stdin in a fresh `bufio.Reader`, whose first fill buffered BOTH lines; the passphrase line died with the buffer when `confirmPrompt` returned, so `readPassphrase`'s `io.ReadAll` saw an empty stream. Fixed with `readLineUnbuffered`: the confirmation now reads one byte at a time and never consumes past its own newline (one `read(2)` per byte is irrelevant for a human's "y"), leaving the rest of stdin intact for whatever reads next — this hardens every confirm-gated command that can be script-driven, not just import. `TestConfirmPromptLeavesRestOfStdinUnread`/`TestConfirmPromptDecline` lock it in; the exact previously-failing pipe was re-run on real hardware and restored all 17 secrets.
- **#71 (`jit migrate remove` left the project's own MCP profile and its vault secrets orphaned — "removed jit from this project" with dangling references still in the global store).** Found in the same E2E test: a project's `.mcp.json` migration writes its profile to the home-rooted global store (an MCP host's subprocess can't do a project-relative lookup), and remove's plan treated *every* global-store profile as a machine-level migration, out of scope by definition — so `mcp-internal-tool` and its two secrets survived the removal, and `jit status` immediately reported them as problems. The `.source` ownership sidecar #56 introduced already records exactly which config file owns each MCP profile, so the fix reads it: a global profile whose sidecar names a config file inside the project tree is part of THIS project — its vault secrets join the deletion plan (and stop counting as "another profile references this" shared paths), its manifest + sidecar are deleted explicitly (they live outside the `.jit/` directory `RemoveAll` covers), and a server entry still launching through jit's `run --profile ... --` wrapper first gets its original command/args and a plaintext env block back via `UnwrapMCPConfig` (`mcpconfig.go`, `ApplyMCPConfig`'s inverse — CURRENT vault values, unmount's semantics, so `jit vault set` edits survive), in the same files-first ordering as the rest of remove. Genuinely machine-level MCP configs (Claude Desktop's) are still untouched, as is any profile whose sidecar points outside the tree. `TestUnwrapMCPConfigRestoresWrappedServer`/`...LeavesForeignWrappersAlone`/`TestRemoveOwnedProfileDeletesManifestAndSidecar`/`TestBuildProjectRemovalPlanClaimsOwnedMCPProfiles` lock it in; verified on real hardware: remove while wrapped → `.mcp.json` back to `npx` + env, zero profiles, empty vault.
- **#72 (`jit migrate home` planned to rewrite `.env` fixtures inside the Go module cache — which would corrupt it).** Found in the same E2E test's `--dry-run`: the home-scope plan listed `~/go/pkg/mod/github.com/subosito/gotenv@v1.6.0/.env` (+`.env.invalid`) as migratable secrets. The module cache holds read-only, checksum-verified copies of PUBLIC module source — a `.env` there is some dependency's test fixture, never this machine's secret, and rewriting one breaks `go mod verify` on a tree the go tool treats as immutable (the write itself would likely fail mid-migration on the read-only permissions, stranding the run after the vault writes). Fixed with `skipDiscoveryDir` (`apply.go`), the shared per-directory gate all four discovery walks (`DiscoverEnvFiles`/`DiscoverMCPConfigs`/`DiscoverNpmrcFiles`/`DiscoverPointerArtifacts`) now use: the existing `migrateNoiseDirs` names plus `goModCacheDir()`, resolved the way the go tool does ($GOMODCACHE, else first $GOPATH element + `pkg/mod`, else `~/go/pkg/mod`). Deliberately migrate-only — `jit audit` still *reports* whatever it finds there; read-only reporting is its job, rewriting is the hazard. `TestDiscoverEnvFilesSkipsGoModCache`/`TestGoModCacheDirFallsBackToHome` lock it in; verified live — the same machine's home plan no longer lists the cache.
- **#65 (`jit migrate undo` of a multi-unit AWS/kubeconfig/Terraform file silently lost every unit but the last — a real data-loss bug).** Found in the 2026-07-12 (round 2) clean-slate DX test: a two-profile `~/.aws/credentials` came back from `jit migrate undo` with the first profile's keys *gone*, only the last-migrated profile's surviving. Root cause is general, not AWS-specific: AWS profiles, kubeconfig users, and Terraform Cloud hosts each migrate multiple *units* out of ONE shared file, applied in a per-unit loop, and every unit's `Apply*` backed up the file it was about to rewrite. So the second profile backed up `~/.aws/credentials` *after* the first was already stripped from it, the third after two were — a chain of progressively-degraded snapshots. `jit migrate undo` restores the most-recent backup per path (`LatestBackups`), so it restored the LAST, most-stripped snapshot. A single-unit file was always fine (only one backup ever taken), which is exactly why this shipped — the test suite had no multi-unit round-trip. The same mechanism left `~/.aws/config`/`~/.terraformrc` that migrate *created* behind on undo (a later unit backed up the just-created file, and that backup won over the first unit's `RemoveOnRestore` record). Fixed with a run-scoped `BackupTracker` (`backuptracker.go`), created once per `jit migrate` run in the CLI and threaded through `ApplyAWSProfile`/`ApplyKubeconfigUser`/`ApplyTerraformHost` (variadic-optional, so a nil tracker means "no dedup — always back up," which is exactly right for the single-unit categories and undo's own pre-restore snapshot): the FIRST backup of each shared file is the only one, capturing the pristine pre-run state, and a file the run creates is recorded once (its `RemoveOnRestore` record never overwritten by a later unit's backup). MCP was already safe (one `ApplyMCPConfig` per file, servers looped inside). `TestApplyAWSMultiProfileUndoRestoresPristine`/`...ExistingConfig...`/`TestApplyTerraformMultiHostUndoRestoresPristine` lock in the full migrate→undo round-trip restoring the pristine file with every unit's secrets and removing jit-created config/rc files.
- **#66 (`jit audit`/`jit migrate` re-detected jit's own in-place pointer files as exposed/migratable secrets on a second run).** Found in the same DX test: after migrating a backup-suffixed `.env.bak`, it's replaced *in place* with pointer content (`API_KEY=jit://vault/...`) but keeps its original name (GAPS.md #34), so the existing name-based skips (`isJitGeneratedEnvArtifact`'s `.pointers` suffix / `.jit-bak-` marker in migrate; `isJitPointerFile` in audit) couldn't catch it. A second `jit migrate local` re-discovered `.env.bak` as a "new" secret and would have migrated its `jit://vault/...` pointer strings as if they were real values; `jit audit` re-reported the git-safe pointer file as an exposed `.env` secret *and* as a suspicious backup filename. Fixed with content-based detection: `LooksLikePointerContent` (migrate) / `isJitPointerContent` (audit, small independent copy per the two packages' no-cross-import convention), both keyed on the pointer file's distinctive first-line header and both guarded to regular files (never opening a live-mount FIFO, which would block). Wired into `DiscoverEnvFiles` (after its FIFO guard), `ScanEnvFiles`, and `ScanSuspiciousFilenames`. `TestDiscoverEnvFilesSkipsInPlacePointerFiles` and `TestScannersSkipInPlacePointerFiles` lock it in.
- **#67 (deleting a migrated project directory without unmounting first left an orphaned mount that permanently blocked `jit vault delete`, with no way out but hand-editing `mounts.yaml`).** Found in the same DX test: `rm -rf`'ing a migrated repo leaves its FIFO mounts registered in `mounts.yaml`; `jit vault delete` then refuses ("N file(s) still live-mounted"), and `jit unmount <path>` — the fix it points you to — itself failed with "profile ... no such file or directory" because the `.jit/profiles/` manifest was deleted with the project. There was no `--force` and no prune command, so the only recovery was editing `mounts.yaml` by hand. Fixed by giving `jit unmount` an orphaned-mount branch: when the mount's profile manifest is gone, there are no secrets to decrypt and nowhere to write them back, so it clears the stale registry entry (and best-effort stops any lingering serve goroutine and removes the `.pointers` companion) after a confirmation — needing no vault auth, since nothing is decrypted and no plaintext is written. This unblocks `jit vault delete` through the exact command its own error already recommends. (The "exit 0 despite error" I also flagged was a false alarm — a shell pipe was masking jit's real non-zero exit code, not jit swallowing it.)
- **#61 (`jit migrate` of a cert-based kubeconfig broke `kubectl` outright — every `kubectl` call after migration failed with `tls: failed to find any PEM data in certificate input`).** Found in the 2026-07-12 clean-slate DX test, reproduced against the real docker-desktop kubeconfig on the machine. The two formats disagree: a kubeconfig's `client-certificate-data`/`client-key-data` fields hold **base64-encoded PEM**, but client-go's ExecCredential protocol wants the **PEM directly** in `status.clientCertificateData`/`clientKeyData` ("PEM-encoded client certificate/key"), never base64. `jit migrate` (`kubeconfig.go`) correctly stores the raw kubeconfig value verbatim in the vault, but `buildK8sExecCredentialOutput` (`internal/cli/k8scred.go`) then copied that base64 straight into the ExecCredential, so kubectl received base64 where it expected `-----BEGIN`. Hit every cert-based kubeconfig — docker-desktop, minikube, kind, kubeadm — i.e. the overwhelmingly common local-dev shape; token-based kubeconfigs were unaffected (a bearer token needs no decode). Fixed with `pemFromKubeconfigData`, which base64-decodes the cert/key fields at emit time, and is deliberately best-effort: a value that isn't valid standard base64 is assumed to already be PEM and passed through unchanged (PEM's leading `-` isn't in the base64 alphabet, so `DecodeString` reliably rejects it), so a hand-set vault entry can never be turned from usable into unusable. AWS `credential_process` and Terraform `credentials_helper` output were verified correct in the same test — this was kube-only. `TestBuildK8sExecCredentialOutputClientCertShape` (rewritten — it previously asserted the base64 passed through, encoding the bug), `TestBuildK8sExecCredentialOutputDecodesRealPEM`, and `TestPemFromKubeconfigDataPassesThroughNonBase64` lock it in; the real-`kubectl`-recovers half is real-hardware verification.

- **#62 (`jit migrate undo` restored `~/.aws/credentials` but left a jit-created `~/.aws/config` behind, leaving both static keys AND a dangling `credential_process`).** Found in the same DX test. `ApplyAWSProfile` backs up `~/.aws/config` before rewriting it — but only `if os.Stat(configPath) == nil` (already exists). For the credentials-only setup the code comment itself names (a fresh AWS CLI that's never run `aws configure`, so no config yet), migrate *creates* the config to hold the `credential_process` line and recorded no backup, so `jit migrate undo` (which iterates `backups.yaml`) had nothing to act on and left the file in place. Post-undo you had the plaintext keys back in `credentials` *and* a `credential_process` pointing at a vault profile in `config` — a confusing dual state, and not the "byte-for-byte" undo promises. Fixed by teaching the undo index about files migration *created*: a new `BackupRecord.RemoveOnRestore` flag (VaultPath empty), written via `RecordCreatedFile` when config didn't pre-exist. `RestoreFromBackup` honors it by snapshotting the current file (so this removal is itself undoable, exactly like the overwrite path) then removing it — and is idempotent, so an already-gone file is success. An *existing* config is still backed up and gets its exact original bytes back, unchanged. `TestApplyAWSProfileNoConfigFileYet` (extended) locks the record + removal + idempotency in.

- **#63 (`jit migrate undo` never reversed the reveal hook migrate wired into `package.json`/`.envrc`, and left the `package.json.jit-bak-<ts>` backup on disk — contradicting the "byte-for-byte" promise and leaking machine-absolute paths).** Found in the same DX test: after `jit migrate undo .`, `package.json` still carried the `predev`/`prestart` reveal hooks (with the absolute `~/go/bin/jit` path and `$HOME`-rooted mount paths baked in — broken and path-leaking if committed for a teammate), and the `.jit-bak` sibling was still there, even though the playground README promised both were cleaned up. Undo only restored vault-backed (secret-bearing) files; the reveal-hook file's plaintext on-disk `.jit-bak` (written by `backupFile`, never indexed in `backups.yaml` on purpose — it holds no secret) was invisible to it. The original design left the hooks deliberately, fearing it might clobber a script the user edited since — a real concern, but the wrong resolution. Fixed with `UninstallRevealHook` (`revealhook.go`), the true surgical inverse of `InstallRevealHook`: it removes only jit's own marked reveal command for the specific mount being undone (matched by a jitPath-independent `agent reveal '<mount>' --quiet` marker, so a jit reinstalled to a different path between migrate and undo is still matched), leaving every other line and every user-authored pre-script segment intact — so it never clobbers a user edit, dissolving the original concern rather than living with it. A partial undo (one of several mounts sharing a directory's hook) keeps the others' hooks AND the `.jit-bak`; only once a hook file has no jit reveal command left are its `.jit-bak-<digits>` siblings cleaned up. `jit migrate undo` calls it per restored mount (best-effort, a failure warns and never fails the file, same as the `.pointers` cleanup beside it), and its `--help` now describes reversing the hook instead of promising to leave it. `TestUninstallRevealHookNpmRemovesHookAndBackup`/`...PreservesUserPreScript`/`...PartialUndoKeepsOtherMount`/`...DirenvRemovesLine`/`...NoOpWhenNothingInstalled` lock the behavior in. (`jit migrate remove`'s `RemoveRevealHooks`, GAPS.md #59, already did the analogous thing for full project removal — this brings plain `undo` in line.)

- **#56 (two same-named MCP servers in different config files silently shared one vault namespace — the later migration overwrote the earlier one's live token).** #55's `claimNamespace` couldn't cover this: its ownership test is "does this store's manifest already claim the path?", and MCP's single global store makes a foreign server's earlier migration indistinguishable from a legitimate re-run of this one. Ownership is now recorded per profile in a `.source` sidecar (a sibling of the manifest naming the config file that created it — a sibling, not a manifest field, because `profile.Profile` is a flat variable→path map every consumer iterates in full). `claimMCPNamespace` (`mcpconfig.go`) claims `mcp-<server>`, or the first free `mcp-<server>-2`/`-3`, by three rules: sidecar matches the migrating config → own profile, refresh freely; sidecar names another file → foreign, bump (reported loudly via `NamespaceMovedFrom`, same as #55); manifest exists with NO sidecar (migrated before this mechanism) → adopt-and-stamp only when every value this server would write is already stored IDENTICALLY — any difference is exactly the silent overwrite this closes, so bump. Unclaimed-but-existing vault paths stay foreign regardless (claimNamespace's own rule), and the sidecar is stamped only AFTER the manifest write, so a crash in between leaves a cautious legacy-shaped profile rather than a false ownership claim. `TestApplyMCPConfigSameServerNameDifferentConfigs`/`...ReRunSameConfigRefreshes`/`...LegacyUnstampedProfile` lock all three rules in.

- **#60 (`jit migrate remove`'s deletion-only path never fired the Touch ID approval its own docs promised).** Reported by the user on the command's very first real run ("it didn't prompt for a fingerprint"): all three removals ran after `jit migrate undo` had already restored the files, so there was nothing to decrypt — and `openVaultFreshAuth()`'s challenge is lazy, firing only on actual key use (wrap/unwrap), while `Vault.Remove` never touches the `KeyWrapper` at all (the same property that lets `jit doctor`/`vault clean` run prompt-free). Combined with `--yes`, a deletion-only remove was effectively ungated. Fixed with `keychainwrap.Wrapper.RequireUserPresence` (an explicit challenge that also primes the MEK cache, so a remove that DOES restore files still prompts exactly once), called unconditionally by `jit migrate remove` right after `openVaultFreshAuth()` — and fail-loud if the fresh-auth wrapper ever stops exposing it, since silently skipping is exactly this bug. Also hardened the same command's deletion loops to tolerate `vault.ErrNotFound` (a manifest referencing an already-`rm`ed/cleaned secret must not strand the removal halfway). `TestRequireUserPresenceChallenges`/`...FailedChallenge` lock the challenge in; the interactive prompt itself was re-verified on real hardware immediately after the fix, both directions: an approved challenge proceeds, and a cancelled one aborts with "Authentication canceled" before any mutation. Deliberately NOT extended to `vault clean`/`delete`: their documented gate is the confirmation prompt (deletion isn't exposure, and the vault files are user-writable anyway); `migrate remove` gets the stronger gate because it was designed and documented around an explicit authentication requirement.

- **#59 (no single verb removed jit from a project completely — undo left `.jit/`, the vault secrets, the backups, and the reveal hooks behind with nothing even saying they were safe to delete by hand).** Raised directly by a dogfooding question ("in which phase does the `.jit` folder get deleted?" — answer: it never was). `jit migrate remove` (`internal/cli/migrateremove.go` + `internal/migrate/remove.go`) now takes jit back OUT of the current project: every registered mount under the tree is unmounted (CURRENT vault values written back — unmount's semantics, not undo's restore-the-backup, so `jit vault set` edits since migration survive), in-place pointer files (`.env.bak`, GAPS.md #34's form) are restored via the new `RestorePointerFile`, `.pointers` companions deleted, then the project's profile manifests, the vault secrets they reference, its `_backups/` entries + undo-index records (`DropBackupRecords`), any reveal hooks (`RemoveRevealHooks`, the true inverse of `InstallRevealHook` — strips only jit's own injected lines, keeps user-authored pre-scripts), and finally the `.jit/` directory itself. Ordering is migrate's own run in reverse: no vault secret is deleted until every file needing its value is back on disk. - **#47 (every serve cycle's `recreateFIFO` rename fed a file-watcher re-read feedback loop — VS Code with the project open re-read the mounts ~30x/sec for hours).** The rename(2) that swapped a fresh pipe in after *every* cycle is a filesystem event; a watcher that re-reads on any change then triggered the next cycle, which renamed again, indefinitely — a real incident on the machine this was investigated on: 635k agent-log lines and 63 CPU-minutes in one afternoon, manual reads racing the watcher for pipe cycles (which made revealing look flaky), and the watcher instantly harvesting real values during every revealed window. A reader that actually drained content still gets the full unconditional rename-over isolation. NOT fixed with a read-end probe after close — a non-blocking write-end open can't tell a lingering stale reader from a brand-new one already blocked in open(2), and stranding that new reader was a real, reproduced empty-read regression during development. `TestServeReusesPipeWhenReaderClosedCleanly` locks it in. - **#24 (`internal/mount.Serve`'s re-open loop could concatenate two cycles' content onto one reader).** Root cause confirmed exactly as suspected: `openForWriteOrCancel`'s blocking `open(O_WRONLY)` only blocks when *zero* readers are attached, so a previous cycle's reader that hadn't yet processed EOF and closed its fd let the next cycle's open succeed immediately against that same stale reader, appending new content onto whatever it was still reading.
  The actual fix isn't the non-blocking-probe approach this entry originally proposed — empirically verified (via a standalone repro against this machine's real FIFO implementation) that a non-blocking `O_WRONLY` probe wakes any reader already blocked in a blocking `open()` waiting for a writer, so a probe that finds "occupied" and backs off can strand a genuinely new reader with a spurious empty read. Building that probe and hitting this exact failure mode directly (not just in theory) is why it was abandoned.
  The shipped fix instead gives every cycle its own kernel pipe object: `recreateFIFO` (`mount.go`) `mkfifo`s a fresh FIFO at a sibling temp path and `rename(2)`s it over the mount path — atomic, so `path` never observably disappears the way a plain remove-then-`mkfifo` would. The ordering of that call is what makes it deadlock-free, and getting it wrong produced a real, reproduced regression during this fix's own development: recreating at the *top* of the loop (before the next `open()`) let a reader that arrived early bind to the fifo about to be orphaned and then block forever on a writer that would never come — worse than the bug it replaced, caught immediately by `TestServeSequentialReaders` hanging for the full 10-minute test timeout under `-race`. The correct placement is right after the current cycle's `f.Write()`, while `f` (this cycle's writer) is still open and *before* `f.Close()` — a reader arriving any time after that point already finds the new fifo in place and rendezvous with the *next* `open()` normally; a stale reader from *this* cycle just keeps talking to the old, now-unlinked pipe once `f.Close()` delivers its EOF.
  `TestServeIsolatesStaleReaderFromNextCycle` locks the fix in with a deterministic repro: a reader that reads one cycle's content, deliberately holds its fd open past when the next cycle starts, must see a clean `io.EOF` (never the next cycle's bytes) on its next read, while a genuinely fresh reader still gets that next cycle's content in full. Verified with `go test ./internal/mount/... -race -count=200` (67s, all green) — the original bug's own repro conditions (`TestServeSequentialReaders` under `-race`) no longer flake at any rate, not just a lower one. Also resolves this entry's own narrow bearing on GAPS.md #2's reveal/hide gate: since a reader can never span two cycles' pipe objects, a hidden cycle's decoy content and a revealed cycle's real content can no longer land in the same reader's stream under any timing.

Fixed in `internal/migrate/plan.go`/`report.go`: `.env` findings are now `CategoryReady` (with a note that real mode only walks the current directory tree, not the whole-machine scan `--dry-run` covers); shell-config/MCP findings are now `CategoryBlocked` with a reason pointing at the manual `jit vault set` + `jit run`/`export` workaround and gap #7.
- **#12 (no `jit unmount`/revert command).** `jit unmount <path>` decrypts the mount's secrets from the vault and writes them back out as a plain dotenv file at the same path, replacing the FIFO — `internal/migrate.UnmountEnvFile` mirrors `ApplyEnvFile`'s reverse direction, and deliberately leaves the vault secrets and profile manifest in place (this reverses the *file*, not the whole migration — "put the plaintext back," not "forget this secret existed"). If `jit agent` is running, `unmount` locks it first (`Client.Lock()`, already-built machinery) to guarantee nothing is mid-`Serve()` on the FIFO before it gets replaced — a real race a naive delete-then-write could otherwise hit (an agent's next write landing on the caller's fresh plaintext). Locks the *whole* agent, not just this one mount, since there's no per-mount stop yet — `jit agent unlock` resumes any other mounts afterward. Verified end-to-end on real hardware: `migrate` → `unmount` round-tripped both variables back to their original plaintext values correctly; each command independently needed its own Touch ID approval since no agent was running to share a session — expected, not a bug (installing the agent first would let them share one).
- **#7 (`jit migrate` real mode only converted `.env` files).** Real mode now also converts shell-config and MCP-config secrets, the two categories gap #7 named. `internal/migrate/shellconfig.go`: `ApplyShellConfig` moves every secret-shaped `export KEY=value` line out of `.zshrc`/`.bashrc`/etc. (RFC.md §4 category 1's own file list, always checked regardless of the current directory since these live at a fixed home path either way) and rewrites the file to load the value back via a single `eval "$(jit export --profile ...)"` call. `internal/migrate/mcpconfig.go`: `ApplyMCPConfig` moves an MCP server's env-block secrets into the vault and rewrites its `command`/`args` to launch via `jit run` instead — using jit's own resolved executable path (`os.Executable` + `EvalSymlinks`, mirroring `jit agent install`'s own logic), since a GUI-launched MCP host's `PATH` often doesn't match an interactive shell's. Both back up the original file first (`<file>.jit-bak-<unix-ts>`, never overwritten by a later run) — a materially bigger safety margin than `.env` migration gets, since a mistake here breaks every future shell session or MCP server launch, not just one file.
  Neither secret is tied to one project directory the way a `.env` file is, so both store their profile in a new home-rooted global store (`profile.GlobalRoot`, `$HOME/.jit/profiles/`) rather than the project-relative `.jit/profiles/` `.env` migration uses — `profile.Load` falls back there when a project-relative lookup misses. This was a deliberate design fork resolved with the user up front (home-rooted global store, chosen over scoping the feature down to shell-config-only or MCP-only) precisely because an MCP host launches its server subprocess with an unpredictable working directory, so a project-relative profile lookup wasn't reliable there. `internal/migrate/plan.go`'s dry-run categorization flipped again accordingly: shell-config/MCP findings are `CategoryReady` again, this time correctly (see the entry above about the same categorization being wrong in both directions).
  **Real incident during verification, not just a design note:** the pre-existing `TestMigrateWithoutDryRunNoEnvFiles` only isolated the working directory (`withFixtureCwd`), never `$HOME` — safe before this change, since real mode's only discovery was cwd-scoped `.env` files. Adding home-scoped shell-config/MCP discovery to the same code path meant that test's `go test` run actually executed real `jit migrate` mutation against the machine running the test suite: it found and migrated the real Claude Desktop MCP config, moving three real secrets into the real production vault and rewriting the config's "jamf" server to launch via the ephemeral `go test` binary path (which stops existing the moment the test run ends) instead of a real `jit` binary — breaking that MCP server until fixed. `ApplyMCPConfig`'s own backup-before-rewrite behavior is what made recovery possible: the original file was restored from `claude_desktop_config.json.jit-bak-<ts>` and verified byte-identical, and the incidentally-created vault entries/profile manifest were removed with the user's explicit confirmation. Fixed by isolating `$HOME` too (`withFixtureHome`) in that test, with a comment recording exactly why cwd isolation alone isn't sufficient for this code path. This is a testing-discipline gap, not a product design flaw — real `jit migrate` scanning the real `$HOME` for shell-config/MCP secrets on every invocation is the intended, approved behavior; the bug was a test that hadn't caught up to a new code path touching state it didn't isolate.

- **#8 (AWS/kubeconfig/npmrc had no migration path).** Scoped to the three RFC-named credential types (Terraform Cloud and GCP application-default-credentials were added to the *scanner* after real-world review, never promised as part of this gap — deferred as new gap #16 instead of attempted alongside these three).
  - **AWS (`~/.aws/credentials`), Tier 2.** `internal/migrate/awscreds.go`'s `ApplyAWSProfile` moves a profile's `aws_access_key_id`/`aws_secret_access_key`/`aws_session_token` into the vault and adds a `credential_process` line to `~/.aws/config` under the correct section — AWS's own irregular convention, a bare `[default]` for the default profile but `[profile <name>]` for every other one, which a naive implementation gets wrong silently. The new `jit aws-credential-process --profile <name>` subcommand is what AWS's CLI/SDK actually invokes, printing the exact `{"Version":1,"AccessKeyId":...}` JSON the `credential_process` protocol requires (no `Expiration` for a static long-term credential, which AWS reads as "never expires"). Both `~/.aws/credentials` and `~/.aws/config` are backed up first; only the known credential keys are removed from the credentials file, leaving its section header and everything else untouched even if the section becomes otherwise empty.
  - **kubeconfig (`~/.kube/config`), Tier 2.** `internal/migrate/kubeconfig.go`'s `ApplyKubeconfigUser` moves a user's bearer `token`, or a complete `client-certificate-data`+`client-key-data` pair, into the vault and replaces it with an `exec` block (`client.authentication.k8s.io/v1`, `interactiveMode: Never`) calling the new `jit k8s-exec-credential --profile <name>` subcommand — client-go's own exec plugin protocol, printing an `ExecCredential` JSON with whichever half (`token` or `clientCertificateData`/`clientKeyData`) the profile actually holds. A user with only one half of a cert/key pair is deliberately skipped rather than migrated — moving half a credential would authenticate even less than the broken kubeconfig it started from. Backed up first.
  - **npmrc (global `~/.npmrc` and project-local `.npmrc`), Tier 4.** Architecturally different from the other two: npm has no native credential-helper hook, and unlike `.env`/shell-config, an npmrc file mixes secrets (`_authToken`/`_password` keys) with ordinary settings (`registry=`, `save-exact=`, ...) that must survive untouched — a dotenv-style "regenerate the whole file from the vault" mount would either lose those settings or wrongly treat them as secrets. This needed genuinely new mount infrastructure rather than reusing `.env`'s: `internal/mount.FormatTemplate` substitutes `${VAR_NAME}` placeholders into an otherwise-verbatim template, `mount.Entry` gained an optional `TemplatePath` field, and both the agent's `mountManager` and `jit unmount` (renamed `UnmountEnvFile` -> `UnmountFile`, now takes a `templatePath` argument) branch on it. `internal/migrate/npmrc.go`'s `ApplyNpmrc` builds that template (secret lines only) and mounts the file as a FIFO like `.env` does. Backed up first.
  - **Shared design decision:** none of AWS/kubeconfig/npmrc secrets are tied to a project directory the caller invokes from (AWS CLI, kubectl, and npm all resolve credentials from an unpredictable cwd) — all three use the home-rooted global profile store (`profile.GlobalRoot`, built for shell-config/MCP in gap #7) rather than a new mechanism.
  - **Two real bugs found and fixed during this build, both via directly running the new tests rather than trusting the implementation by inspection:**
    1. `npmrcVarName`'s sanitizer left a double underscore (`REGISTRY_NPMJS_ORG__AUTHTOKEN`) when a replaced invalid-character run sat immediately next to an original literal underscore (e.g. `/:` before `_authToken`) — a collapse-repeated-underscores pass was missing. Caught immediately by `TestNpmrcVarNameSanitization`'s exact-match assertion.
    2. `DiscoverNpmrcFiles`'s check for the fixed global `~/.npmrc` path never guarded against the file already being a FIFO (from an earlier migration) before reading it — opening a FIFO for read blocks until a writer connects, so a second migration attempt with no agent running would hang the scan forever. `DiscoverEnvFiles` already guards this way for its own cwd walk; the fixed global-path check needed the same `os.Lstat`+`ModeNamedPipe` guard independently. Caught by `TestApplyNpmrcIsIdempotentAndMergesOnSecondRun` timing out at exactly the `readLines` call in a stack trace, not a silent pass.
  - Verified via the full automated test suite (including the two bugs above) with `$HOME`/cwd fully isolated in every new test, informed directly by the gap #7 incident's lesson above — not yet verified end-to-end against a real AWS/kubectl/npm invocation on real hardware, unlike every other credential-touching feature this session (needs a real Touch ID approval this tool can't script).

- **#17 (real `jit migrate` had no confirmation gate).** Real mode now prints the same kind of per-category plan `--dry-run` shows (`printMigratePlan` in `internal/cli/migrate.go`, grouped by `.env`/shell-config/MCP/AWS/kubeconfig/npmrc, backed by the same `Discover*` results the rest of `RunE` already had in hand) and requires a `[y/N]` confirmation before mutating anything — `--yes` skips the prompt for scripting, matching `vault set`/`vault rm`'s existing `--force`/prompt pattern. Deliberately placed *before* `openVault()`: declining must never trigger a Touch ID prompt for work about to be aborted anyway. Verified with `TestMigrateWithoutDryRunDeclinedConfirmationAborts` (plants a real shell-config finding, declines via empty stdin, asserts the file is byte-for-byte unchanged and the run never reached the vault) — the accept path (`--yes` or a `y` answer) still needs real-hardware verification like every other vault-touching command, since it exercises `openVault()`.
- **#18 (`jit agent install`'s TTL was unconfigurable).** `agent install` now takes its own `--ttl` flag (same 15m default as `agent run --ttl`) and bakes it into the installed plist's `ProgramArguments` (`--ttl <value>` appended after `agent run`). Also fixed a latent problem this surfaced: re-running `install` to change the TTL rewrote the plist file but never restarted the already-loaded launchd job, so the new value wouldn't take effect until next login — `install` now unloads any previously-installed instance (best-effort, `os.Stat` first so a first-ever install has nothing to unload) before loading the freshly-written plist. Not independently verified against real `launchctl` on this machine (would require actually installing/reinstalling the LaunchAgent) — same manual-verification constraint as the rest of `jit agent install`.
