# Security Review, July 2026

**Date:** 2026-07-11
**Scope reviewed:** `cmd/`, `internal/` at the Phase 1 build (all shipped commands)
**Type:** Internal security review, AI-assisted static analysis + on-host verification.
**Conducted with:** Anthropic's **Claude Opus 4.8** (via Claude Code), driven and reviewed by the maintainer.
**Not** an independent third-party audit, see [Honesty about this document](#honesty-about-this-document).

This is a snapshot of a deliberate security pass over the `jit` codebase: what we
looked at, what we found, what we fixed, and, just as importantly, the limits we
*didn't* fix because they're inherent to the current Phase 1 design and are called
out openly (the README's security-model section, and the known-limitations
list at the end of this report).
We publish it because a tool that holds your secrets should be legible about its own
security posture, not just assert that it has one.

---

## What we reviewed

The review focused on the security-load-bearing paths, read in full:

- **Cryptography**, `internal/vault` (envelope encryption, per-secret AES-256-GCM,
  the passphrase-based export) and `internal/keychainwrap` (the master-key wrapper).
- **The agent**, `internal/agent` (the Unix-socket session broker: peer
  authentication, session TTL, the wrap/unwrap protocol).
- **The live-mount decoy gate**, `internal/mount` (decoy-by-default serving, the
  reveal window, named-pipe isolation).
- **The mutating paths**, `internal/migrate` (how plaintext credentials are moved
  into the vault, how originals are backed up, how `jit migrate undo` restores them)
  and the on-disk wrappers migration writes (AWS `credential_process`, kubeconfig
  `exec`, Terraform helper, MCP `jit run` wrapper, shell `eval` line).
- **On-disk state**, file and directory permissions across the vault, backups,
  agent socket, and logs, verified on a real machine.

Methodology: full source read of the above, targeted adversarial analysis for
command/code injection, path traversal, TOCTOU/symlink races, weak crypto, secret
leakage, and permission errors, plus live inspection of the on-disk artifacts and
the keychain item on a running install.

## Threat model, what jit protects, and what it does not (yet)

This is the part every user should read. jit's protection depends entirely on
**where an attacker is standing**.

**You are protected against:**

- **A lost or stolen device (locked, or powered off with FileVault).** Secrets are
  AES-256-GCM encrypted at rest; the master key is marked
  *available only when this specific device is unlocked*; the encrypted files are
  useless if copied to another machine.
- **A different user account on a shared machine.** The vault directory is `0700`,
  the agent socket is `0600`, and the agent additionally verifies the connecting
  process's OS user (`LOCAL_PEERCRED`) before serving anything, a different user
  cannot reach the vault or the session.

**You are NOT fully protected against, by design, in Phase 1:**

- **Malicious code already running as *your own* user.** In the current build the
  master key is stored as a standard macOS Keychain item and jit's Touch ID prompt
  is enforced in the application, not by the operating system's key-release policy.
  An attacker who already has code execution as you can either read that key
  directly or ride the agent's unlocked session, the agent's authentication check
  is "same user," which is exactly the attacker's position. This is a
  documented, accepted boundary of the current build, and the planned remedy is Secure
  Enclave-bound key storage (`internal/secureenclave`), which makes key release
  OS-enforced and biometric-gated. It's built but not yet wired up. (*Correction,
  2026-07-30:* this originally said it was "blocked on an Apple Developer ID
  signing identity." The spike that followed showed the identity is necessary but
  not sufficient: SE persistence needs a provisioning-profile entitlement that
  only an `.app` bundle can carry, so the real dependency is shipping the agent
  as a bundled daemon; see `spike/secure-enclave/FINDINGS.md`.)

In short: **jit meaningfully raises the bar against device theft and multi-user
exposure today; it does not claim to defend against malware running as you until
Secure Enclave binding ships.** We'd rather say that plainly than let "encrypted
vault" imply more than it currently delivers.

## Findings and remediations

| # | Severity | Finding | Status |
|---|----------|---------|--------|
| 1 | Medium | `jit migrate undo` restored a backup to the path named in `backups.yaml`, an unencrypted, unauthenticated index, with no validation. A tampered or corrupted index could redirect a decrypted secret to an arbitrary destination, using the user's own authenticated undo. | **Fixed** |
| 2 | Low–Med | The restore write followed symlinks and was non-atomic (a `remove`-then-write with a race window), compounding #1: a symlink planted at the destination could redirect the write. | **Fixed** |
| 3 | Low | The agent log was created world-readable (`0644`). It contains no secret values, but it does record reader process lineage (pids, executable paths, mount paths). Mitigated in practice by the `0700` parent directory, but tightened regardless. | **Fixed** |
| 4 | Low | The AWS profile name was interpolated into the `credential_process` line without quoting. Not reachable in practice (the name is constrained to a safe character set upstream by the vault path sanitizer before this line runs), but the safety shouldn't depend on that ordering. | **Fixed (defense-in-depth)** |

### Remediation detail

- **#1 / #2**, `jit migrate undo` now validates every restore destination
  (absolute + canonical, no `..`) before writing, and performs the write with
  `O_CREATE | O_EXCL | O_NOFOLLOW` so it can never follow a symlink or clobber
  something that reappeared at the path, it lands at exactly the validated path or
  fails loud. Regression tests cover the rejection of untrustworthy paths and the
  symlink-redirect case.
- **#3**, the agent tightens its log to `0600` on every start, covering both fresh
  logs and any left behind by an older build.
- **#4**, the AWS profile name is now quoted consistently with the executable path,
  so the line is safe on its own terms rather than by relying on upstream
  sanitization order.

## What we verified as sound

Not everything gets a finding, several areas were examined specifically because
they're security-critical, and held up:

- **Cryptography.** AES-256-GCM with a fresh random data-key per secret and random
  nonces; a cleanly separated, passphrase-based (Argon2id, 64 MiB) export scheme for
  disaster recovery. No home-grown crypto, no reused nonces, no ECB-shaped mistakes.
- **Secret-path handling.** The vault rejects `..` and non-whitelisted characters and
  re-checks the resolved path stays inside the vault directory, genuine
  defense-in-depth against traversal.
- **The agent's peer authentication.** Same-user enforcement over the socket is
  correct and is not weakened to "any local connection."
- **The live-mount decoy gate.** Mounts serve recognizably-fake placeholder values by
  default and only real content during a short, explicitly-triggered, capped window;
  the real-vs-decoy decision is made live on every read, and the reveal duration is
  clamped server-side.
- **The migration wrappers.** No secret *value* is ever written into a shell line,
  script, or config file, values go only to the vault. The reveal hooks that edit
  `.envrc`/`package.json` use proper shell-quoting and a real JSON encoder. Backups of
  the original plaintext files are genuinely encrypted with the vault key, not copied
  to a plaintext sibling.
- **On-disk permissions.** `0700` directories, `0600` files and socket, verified live.

## Known, accepted limitations

These are not defects to be filed, they are documented boundaries of the current
build, tracked openly:

- The master-key protection is application-enforced, not OS-enforced, until Secure
  Enclave binding ships.
- In-memory secret wiping is best-effort (Go gives no guarantee against a GC-moved
  copy or a swapped page); stronger in-memory hardening is a deferred upgrade.
- Migration's in-place config rewrites (`~/.aws/config`, `~/.zshrc`, etc.) are not
  atomic. These files hold no plaintext secret after migration, and the original is
  always encrypted-backed-up first, but a crash mid-rewrite could leave one
  truncated. Tracked as a robustness item, not a confidentiality one.

The full gap list, everywhere current behavior falls short of the target
design, is maintained in the project's internal design docs; the items above
are the security-relevant ones.
